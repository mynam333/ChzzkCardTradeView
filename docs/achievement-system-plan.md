# 업적 시스템 기획서

## 1. 목표

치카포의 기존 카드 수집, 가챠, 한계돌파, 판매, 1:1 교환, 오픈마켓, 미니게임, 상점, 칭호, 쿠폰, 친구/채팅, 신고/관리 흐름을 업적으로 연결한다.

핵심 목표는 세 가지다.

- 관리자가 코드 배포 없이 업적을 만들고, 조건과 보상을 조정할 수 있다.
- 유저는 내 업적 진행도, 완료 여부, 보상 수령 상태를 정렬/필터로 확인할 수 있다.
- 숨겨진 업적은 달성 전까지 이름, 설명, 조건, 진행도를 가리고, 달성 후에만 공개한다.

## 2. 현재 서비스 기준 활용 가능 정보

현재 코드 기준으로 업적 조건에 활용하기 좋은 정보는 다음과 같다.

- 유저: 가입일, 마지막 접속, 포인트, 대표 카드, 상태 메시지, 칭호 장착
- 카드: 보유 카드, 스트리머 채널, 별 등급, 획득 시각, 숨김/잠금/즐겨찾기, 장착 코스메틱
- 가챠/소환: 카드 획득, 무료 소환권, 보너스 무료 소환권, 포인트 차감
- 한계돌파: 대상 카드 별 상승, 재료 카드 소모
- 카드 판매: 판매 수량, 별 등급, 획득 포인트
- 1:1 교환: 제안, 확인, 최종 성사, 거절/취소, 제시 포인트/카드
- 오픈마켓: 등록, 즉시구매, 경매 입찰, 낙찰, 관심 조건, 판매/구매 이력
- 미니게임: 게임 타입, 성공/실패, 정답 수, 획득 포인트, 연습 모드, 티켓
- 상점/코스메틱: 아이템 구매, 장착, 해제, 보유 수량
- 칭호: 보유 칭호, 장착 칭호, 구독 연동 칭호
- 쿠폰: 쿠폰 사용, 다중 보상 수령
- 친구/채팅: 친구 신청/수락, 채팅방, 메시지/첨부 사용
- 신고/관리: 신고 접수, 신고 처리 결과, 카드 이미지 관리
- 자산 감사 로그: `asset_event_logs`에 카드/포인트/코스메틱/티켓/칭호 자산 변동 기록이 이미 존재

## 3. 업적 분류

유저 화면에서는 아래 카테고리로 묶는다.

- 시작: 가입, 첫 카드, 첫 대표 카드, 첫 상태 메시지
- 수집: 카드 수, 스트리머 수, 별 등급, 특정 조합, 희귀 카드
- 성장: 한계돌파, 5성 달성, 잠금/즐겨찾기/숨김 활용
- 경제: 포인트 획득/사용, 카드 판매, 상점 구매, 코스메틱 보유
- 교환: 1:1 거래 제안/성사, 교환으로 특정 카드 획득
- 마켓: 판매 등록, 구매, 경매 입찰/낙찰, 관심 조건
- 미니게임: 게임별 성공, 연속 성공, 빠른 성공, 퍼펙트
- 커뮤니티: 친구, 채팅, 푸시 구독, 신고
- 스트리머: 스트리머 등록, 내 채널 카드 이미지 관리, 라이브/시세 관련
- 이벤트: 기간 한정, 쿠폰/운영 이벤트
- 숨겨진 업적: 조건 비공개, 달성 후 공개

## 4. 업적 종류 예시

### 시작 업적

- 첫 로그인: 계정 생성 후 최초 접속
- 첫 소환: 카드 1장 획득
- 내 얼굴 만들기: 대표 카드 설정
- 한 줄 소개: 상태 메시지 등록
- 첫 칭호: 칭호 1개 보유
- 오늘의 출석: 하루 접속
- 돌아온 유저: 7일 이상 미접속 후 접속

### 수집 업적

- 카드 수집가 I~V: 카드 총 10/50/100/300/1000장 보유
- 다양한 취향: 서로 다른 스트리머 카드 10/30/100종 보유
- 별을 모으는 사람: 1성 이상 카드 10장 보유
- 별자리 완성: 5성 카드 1/3/10장 보유
- 한 스트리머 올컬렉션: 동일 스트리머 0~5성 모두 보유
- 같은 마음 여러 장: 동일 스트리머 동일 별 카드 10장 보유
- 잠금 습관: 카드 10장 잠금
- 비밀 보관함: 카드 10장 숨김
- 최애 정리: 즐겨찾기 카드 5장 설정

### 성장 업적

- 첫 한계돌파: 카드 합성 1회
- 별의 계단: 한계돌파로 3성 달성
- 최고 등급: 한계돌파로 5성 달성
- 재료 장인: 한계돌파 재료 카드 누적 50장 사용
- 신중한 수집가: 5성 카드를 잠금
- 대표의 품격: 5성 카드를 대표 카드로 설정

### 경제 업적

- 첫 판매: 카드 판매 1회
- 카드 정리왕: 카드 누적 100장 판매
- 소소한 수익: 카드 판매로 10만 P 획득
- 큰손: 상점 아이템 10개 구매
- 꾸미기 입문: 코스메틱 1개 장착
- 꾸미기 전문가: 카드 테두리와 이름 효과를 모두 장착
- 백만장자: 포인트 잔액 100만 P 도달
- 회전율 좋은 지갑: 누적 포인트 사용 100만 P

### 교환 업적

- 첫 제안: 1:1 교환 제안 1회
- 성사된 거래: 1:1 교환 성사 1회
- 교환 중개자: 1:1 교환 성사 10회
- 카드와 포인트: 카드와 포인트를 함께 포함한 교환 성사
- 코스메틱 포함 거래: 코스메틱 포함 교환 성사
- 쌍방 합의: 내가 보낸 제안이 최종 승인됨

### 마켓 업적

- 첫 판매 등록: 오픈마켓 등록 1회
- 첫 구매: 오픈마켓 구매 1회
- 첫 낙찰: 경매 낙찰 1회
- 입찰 경쟁자: 경매 입찰 10회
- 시장 감시자: 마켓 관심 조건 3개 등록
- 판매 완료: 오픈마켓 판매 성사 10회
- 빠른 거래: 등록 후 10분 이내 판매 성사

### 미니게임 업적

- 첫 승리: 미니게임 성공 1회
- 데일리 플레이어: 오늘의 미니게임 7일 참여
- 퀴즈왕: 퀴즈 10회 성공
- 퍼즐러: 퍼즐 10회 성공
- 짝맞추기 달인: 매치 10회 성공
- 시세 감각: 시세 듀얼 퍼펙트
- 확대 탐정: 카드 확대 탐정 퍼펙트
- 번개 손: 퀴즈 3초 보너스 달성
- 퍼즐 스프린터: 퍼즐 30초 보너스 달성
- 전승 행진: 미니게임 5연속 성공

### 커뮤니티 업적

- 첫 친구: 친구 1명 추가
- 인맥 관리: 친구 10명 보유
- 첫 대화: 1:1 톡 메시지 1개 전송
- 이미지 공유: 채팅 이미지 첨부 1회
- 알림 준비 완료: 푸시 구독 등록
- 깨끗한 카드 환경: 카드 신고 1회 접수
- 신고 결과 확인: 신고 처리 결과 알림 확인

### 스트리머/방송 관련 업적

- 발굴자: 신규 스트리머 등록
- 내 카드 관리: 내 채널 카드 이미지 업로드
- 별 이미지 장인: 별 등급별 카드 이미지 3개 이상 등록
- 라이브 수집가: 라이브 중인 스트리머 카드 획득
- 시세 감시자: 스트리머 상세 시세 그래프 조회
- 상승장 포착: 24시간 상승률이 높은 카드 획득

### 숨겨진 업적 예시

- 뜻밖의 행운: 특정 낮은 확률 조건 달성
- 완벽한 하루: 하루 안에 소환, 미니게임 성공, 거래 성사, 상점 구매를 모두 수행
- 조용한 수집가: 숨김 카드만 일정 수 이상 보유
- 아무도 모르게: 숨겨진 업적 첫 달성
- 시장의 눈: 관심 조건 등록 후 해당 조건 매물을 구매
- 별의 마지막 조각: 동일 스트리머 0~5성 완성

숨겨진 업적은 달성 전 카드에 `???`, `숨겨진 업적`, `조건을 달성하면 공개됩니다`만 표시한다. 진행률, 목표 수치, 보상 상세도 기본적으로 숨긴다. 단, 관리자 설정으로 “힌트 공개”를 켤 수 있다.

## 6. 조건 DSL

관리자가 직접 JSON을 작성하지 않아도 되도록 UI 빌더를 제공하되, 저장은 JSON DSL로 통일한다.

단일 조건 예시:

```json
{
  "type": "counter",
  "metric": "card.acquired.count",
  "operator": ">=",
  "target": 100,
  "filters": {
    "star": { "gte": 1 }
  }
}
```

스냅샷 조건 예시:

```json
{
  "type": "snapshot",
  "metric": "inventory.unique_streamer_count",
  "operator": ">=",
  "target": 30
}
```

복합 조건 예시:

```json
{
  "type": "all",
  "conditions": [
    { "type": "counter", "metric": "minigame.success.count", "target": 1 },
    { "type": "counter", "metric": "market.purchase.count", "target": 1 },
    { "type": "counter", "metric": "shop.purchase.count", "target": 1 }
  ],
  "window": {
    "type": "calendar_day",
    "timezone": "Asia/Seoul"
  }
}
```

## 8. 보상 모델

쿠폰의 다중 보상 구조를 확장해 재사용한다.

지원 보상:

- 포인트: `point`
- 카드: `card`
- 코스메틱: `cosmetic`
- 미니게임 티켓: `minigame_ticket`
- 무료 소환 티켓: `free_draw_ticket`
- 칭호: `title`
- 업적 전용 배지 또는 프로필 장식: 추후 확장

보상 지급 방식:

- 기본은 `manual`: 유저가 업적 화면에서 직접 수령
- 이벤트성 즉시 보상은 `auto`: 완료 시 자동 지급
- 보상 지급은 멱등 처리한다. 같은 `user_id + achievement_id + repeat_key`는 1회만 지급한다.
- 지급 성공 후 알림을 생성한다.

## 9. 진행도 갱신 방식

업적은 세 가지 방식으로 처리한다.

### 1. 이벤트 기반 증가

액션이 발생한 시점에 진행도를 증가시킨다.

적합한 조건:

- 소환 횟수
- 판매 횟수
- 교환 성사 횟수
- 마켓 구매/판매/입찰
- 미니게임 성공
- 상점 구매
- 친구/채팅 횟수

기존 `asset_event_logs`에 남는 자산 변동은 최대한 재사용한다. 자산 변동이 아닌 행동은 `achievement_events`에 기록한다.

### 2. 스냅샷 재계산

현재 상태를 조회해서 진행도를 계산한다.

적합한 조건:

- 현재 카드 보유 수
- 현재 5성 카드 수
- 현재 포인트 잔액
- 현재 친구 수
- 현재 보유 칭호/코스메틱 수
- 동일 스트리머 0~5성 보유 여부

이 방식은 카드 판매/교환/탈퇴 등으로 상태가 줄어들 수 있으므로, 업적 정책을 정한다.

- 기본 정책: 한 번 완료한 업적은 취소하지 않는다.
- 진행 중 업적: 현재 상태 기준으로 감소 가능
- 이벤트 한정 업적: 기간 종료 시 더 이상 진행 불가

### 3. 복합/시퀀스 판정

여러 이벤트가 특정 기간 안에 발생했는지 본다.

예:

- 하루 안에 미니게임 성공 + 마켓 구매 + 상점 구매
- 등록 후 10분 안에 마켓 판매 완료
- 7일 연속 접속

복잡한 조건은 `achievement_events`를 기반으로 배치 평가한다.

## 10. 관리자 페이지 기획

관리자 페이지에 `업적` 탭을 추가한다.

### 목록 화면

기능:

- 검색: 이름, 코드, 설명
- 필터: 활성/비활성, 숨김 여부, 카테고리, 반복 정책, 보상 타입
- 정렬: 생성일, 수정일, 표시 순서, 달성자 수, 완료율
- 표시 정보: 이름, 카테고리, 숨김, 기간, 조건 요약, 보상 요약, 활성 상태
- 빠른 액션: 활성화/비활성화, 복제, 수정, 미리보기

### 생성/수정 화면

섹션:

- 기본 정보: 이름, 설명, 카테고리, 아이콘, 등급, 표시 순서
- 노출 설정: 숨김 여부, 힌트, 기간, 반복 정책
- 조건 빌더: 메트릭 선택, 필터, 목표값, AND/OR 그룹
- 보상 빌더: 포인트, 카드, 코스메틱, 티켓, 칭호 다중 추가
- 지급 설정: 자동 지급/직접 수령
- 테스트: 특정 유저 ID를 넣고 현재 진행도 계산 미리보기

### 운영 도구

- 업적별 달성자 목록
- 업적별 보상 지급 로그
- 특정 유저의 업적 진행도 재계산
- 전체 업적 재평가 배치 실행
- 숨겨진 업적 미리보기
- 기간 종료/시작 예약 확인

### 정렬

## 12. API 초안

유저 API:

- `GET /achievements`
  - 내 업적 목록
  - 쿼리: `status`, `category`, `hidden`, `sort`, `limit`, `cursor`
- `GET /achievements/summary`
  - 완료 수, 수령 가능 수, 카테고리 요약
- `POST /achievements/:id/claim`
  - 보상 수령
- `POST /achievements/recalculate`
  - 내 진행도 재계산 요청. 남용 방지를 위해 쿨다운 적용

관리자 API:

- `GET /admin/achievements`
- `POST /admin/achievements`
- `PUT /admin/achievements/:id`
- `POST /admin/achievements/:id/toggle`
- `POST /admin/achievements/:id/duplicate`
- `GET /admin/achievements/:id/users`
- `GET /admin/achievements/:id/grants`
- `POST /admin/achievements/evaluate`
- `POST /admin/users/:user_id/achievements/recalculate`

## 13. 보안/어뷰징 기준

- 클라이언트가 진행도를 직접 올릴 수 없게 한다.
- 모든 진행도 증가는 서버 액션 성공 이후에만 기록한다.
- 보상 지급은 DB 트랜잭션 또는 멱등 키로 중복 지급을 차단한다.
- 마켓/거래/가챠처럼 금전성 자산이 움직이는 기능은 기존 원자 처리 이후에 업적 이벤트를 기록한다.
- 숨겨진 업적의 조건은 API 응답에서 내려주지 않는다.
- 관리자 조건 빌더는 허용된 메트릭과 필터만 저장할 수 있게 검증한다.
- 채팅/친구 업적은 내용이 아니라 횟수와 상태만 사용한다.
- 신고 업적은 허위 신고 유도를 막기 위해 과도한 반복 보상을 피한다.

## 14. 배치/성능 전략

- 이벤트 기반 업적은 액션 완료 후 빠르게 업데이트한다.
- 스냅샷 업적은 로그인, 내 업적 페이지 진입, 주요 자산 변경 후 지연 평가한다.
- 대량 재계산은 관리자 배치에서 페이지 단위로 처리한다.
- 업적 정의는 메모리 캐시한다. 관리자 수정 시 캐시를 무효화한다.
- 유저 업적 목록은 `user_id + status + category` 인덱스를 둔다.
- 숨겨진 업적은 서버에서 마스킹한 DTO만 내려준다.

## 17. 주요 의사결정

- 업적 보상은 쿠폰 보상 구조를 확장해 재사용한다.
- 숨겨진 업적은 서버 응답 단계에서 마스킹한다.
- 코드 배포 없이 업적을 추가하기 위해 조건은 JSON DSL로 저장한다.
- 모든 업적을 이벤트 기반으로만 처리하지 않고, 현재 보유 상태가 중요한 업적은 스냅샷 계산을 병행한다.
- 완료된 업적은 원칙적으로 회수하지 않는다.
- 보상은 기본적으로 유저가 직접 수령하게 하여 “받을 보상” 경험을 만든다.

## 18. 활용 정보 확장안

현재 DB에 이미 남는 자산 이벤트만으로도 많은 업적을 만들 수 있지만, 업적의 다양성을 크게 늘리려면 “행동 이벤트”, “상태 스냅샷”, “파생 지표”를 추가로 설계하는 것이 좋다.

원칙은 다음과 같다.

- 클라이언트가 임의 전송한 값은 보상 업적의 근거로 쓰지 않는다.
- 서버 액션이 성공한 뒤 서버가 직접 이벤트를 기록한다.
- 채팅 내용, 검색어 원문, 쿠폰 코드 원문처럼 민감하거나 악용 여지가 큰 값은 업적 데이터에 저장하지 않는다.
- 업적에 필요한 최소 메타데이터만 저장한다.
- 확장 이벤트는 영구 보존하되, 쓰기 경로와 조회 경로를 분리해 DB/백엔드 부하를 제한한다.
- 반복 행동을 유도하면 스팸이 될 수 있는 영역은 “횟수 업적”보다 “최초 1회/품질 판정/운영 승인” 중심으로 설계한다.

## 19. 영구 기록과 부하 제어 설계

확장 정보는 영구적으로 남겨야 하지만, 모든 요청마다 무거운 업적 평가를 실행하면 백엔드와 DB에 부담이 된다. 따라서 저장, 집계, 평가, 조회를 분리한다.

핵심 구조:

- `achievement_events`: 영구 원본 이벤트. 작고 append-only로 기록한다.
- `user_achievement_stats`: 유저별 누적 집계. 업적 조건과 화면 조회는 대부분 이 테이블을 읽는다.
- `user_achievements`: 업적별 진행/완료/수령 상태. 유저 화면의 주 데이터다.
- `achievement_evaluation_queue`: 무거운 재계산이 필요한 유저를 비동기로 처리하기 위한 큐다.

### 19.1 원본 이벤트 저장 원칙

`achievement_events`는 영구 보존 원장으로 둔다. 단, 이벤트 1건을 작게 유지한다.

저장 원칙:

- append-only insert만 한다. 기존 이벤트를 수정하지 않는다.
- `event_key` unique로 중복 기록을 막는다.
- 큰 JSON을 저장하지 않는다. 필요한 ID, 숫자, boolean, 짧은 enum만 저장한다.
- 화면 표시용 이름, 이미지 URL, 긴 설명은 저장하지 않는다. 필요하면 기존 테이블에서 조인하거나 당시 스냅샷이 꼭 필요한 경우 짧은 값만 저장한다.
- 채팅 메시지 원문, 검색어 원문, 쿠폰 코드 원문은 저장하지 않는다.
- 이벤트 발생 시간이 중요한 업적을 위해 `occurred_at`은 항상 저장한다.
- 관리자/감사용 조회가 가능하도록 삭제하지 않는다.

권장 인덱스:

- unique: `event_key`
- index: `(user_id, id)`
- index: `(user_id, event_type, id)`
- index: `(event_type, occurred_at)`
- index: `(source_type, source_id)`

인덱스는 과하게 만들지 않는다. 업적 평가는 대부분 `user_achievement_stats`를 읽게 하고, 원본 이벤트는 감사/재집계/특수 조건에만 사용한다.

### 19.2 쓰기 경로 부하 제어

서비스 본 기능의 성공 응답이 업적 처리 때문에 느려지면 안 된다.

쓰기 방식:

- 핵심 자산 이동은 기존 트랜잭션이 끝난 뒤 업적 이벤트를 기록한다.
- 이벤트 insert 실패가 본 기능 성공을 되돌리지 않게 한다. 단, 실패 로그를 남기고 재시도 큐에 넣는다.
- 같은 요청에서 여러 업적 이벤트가 생기면 bulk insert로 묶는다.
- 이벤트 기록 함수는 비동기 best-effort를 기본으로 하되, 보상 중복과 직접 관련된 이벤트는 멱등 키를 사용한다.
- 고빈도 이벤트는 즉시 업적 전체 평가를 하지 않고 집계값 증가만 수행한다.

예시:

- 카드 10연속 뽑기: 이벤트 10건을 개별 평가하지 않고, 획득 이벤트 bulk insert 후 `card.acquired.count += 10`, 별 등급별 집계를 한 번만 갱신한다.
- 채팅 메시지: 모든 메시지마다 업적 목록을 평가하지 않고, 일일 인정 상한 내에서 `chat.message.count`만 증가시킨다.
- 화면 진입: 보상성이 낮으므로 같은 유저/이벤트/일자 기준으로 1일 1회만 기록한다.

### 19.3 집계 테이블 중심 평가

대부분의 업적 조건은 원본 이벤트를 매번 세지 않고 `user_achievement_stats`에서 읽는다.

예:

- `card.acquired.count`
- `card.star.5.acquired.count`
- `inventory.card_count`
- `market.purchase.count`
- `minigame.success.quiz.count`
- `minigame.perfect.count`
- `login.current_streak_days`

집계 갱신 방식:

- 단순 카운터: 이벤트 발생 시 즉시 `stat_value = stat_value + delta`
- 현재 상태형: 보관함/친구/코스메틱처럼 변동이 큰 경우 액션 성공 후 해당 유저만 재계산
- 무거운 조건: 큐에 넣고 워커가 지연 재계산
- 연속 접속: 하루 첫 접속 이벤트에서만 계산

`user_achievement_stats`는 “빠른 조회용 캐시”지만, 원본 이벤트가 영구 보존되므로 장애 시 재생성 가능하다.

### 19.4 평가 큐

복합 조건, 시즌 조건, 누락 보정은 요청 처리 중 직접 계산하지 않는다.

추천 테이블: `achievement_evaluation_queue`

- `id`
- `user_id`
- `reason`
- `priority`
- `dedupe_key`
- `run_after`
- `attempts`
- `locked_at`
- `created_at`

동작:

- 이벤트 기록 후 필요한 경우 큐에 `user_id + reason` 단위로 넣는다.
- `dedupe_key` unique로 같은 유저의 같은 평가 요청이 중복 쌓이지 않게 한다.
- 워커는 작은 batch 단위로 처리한다.
- 실패 시 attempts를 올리고 backoff를 둔다.
- 유저 화면 진입 시 큐가 밀려 있어도 기존 진행도를 먼저 보여주고, 필요하면 “갱신 중” 상태만 표시한다.

### 19.5 유저 화면 조회 최적화

업적 화면은 원본 이벤트를 직접 조회하지 않는다.

조회 흐름:

1. 활성 업적 정의 캐시를 읽는다.
2. `user_achievements`에서 해당 유저 진행 상태를 읽는다.
3. 필요한 경우 `user_achievement_stats`에서 최신 집계만 보강한다.
4. 숨겨진 미달성 업적은 서버에서 마스킹한다.

업적 정의는 변경 빈도가 낮으므로 메모리 캐시한다. 관리자 수정 시 캐시를 무효화한다.

권장 인덱스:

- `user_achievements`: `(user_id, status)`, `(user_id, achievement_id, repeat_key)` unique
- `user_achievement_stats`: `(user_id, stat_key)` unique
- `achievements`: `(is_active, sort_order)`, `(category, is_active)`

### 19.6 영구 보존과 테이블 크기 대응

영구 보존을 하더라도 테이블 크기와 인덱스 부하는 관리해야 한다.

운영 기준:

- 원본 이벤트는 작은 row로 저장한다.
- 이벤트 타입별 메타데이터 스키마를 제한한다.
- 무분별한 인덱스를 피한다.
- 관리자 감사 조회는 최신순 페이지네이션만 제공한다.
- 오래된 이벤트를 조회할 때는 `id` 또는 `occurred_at` 기반 cursor를 사용한다.
- MySQL 운영에서는 월/분기 단위 파티셔닝을 검토할 수 있다.
- SQLite 운영에서는 이벤트가 많아지면 MySQL 전환을 권장한다.

보존 정책:

- 업적 원본 이벤트는 삭제하지 않는 것을 기본으로 한다.
- 개인정보 원문이 없도록 설계해 영구 보존 부담을 줄인다.
- 회원 탈퇴 시 일반 개인정보와 연결되는 화면 노출은 제거하되, 감사/무결성 목적의 익명화된 이벤트 보존 정책을 별도로 정한다.

### 19.7 이벤트 등급

모든 확장 정보를 같은 강도로 기록하지 않는다.

#### A등급: 자산/보상 핵심 이벤트

반드시 영구 기록한다.

- 카드 획득/판매/한계돌파
- 포인트 획득/사용
- 마켓 구매/판매/입찰/낙찰
- 1:1 교환 성사
- 상점 구매
- 코스메틱 지급/장착
- 칭호 지급/장착
- 업적 보상 지급

처리:

- 멱등 키 필수
- 원본 이벤트 기록
- 집계 즉시 갱신
- 보상 관련 업적 평가 우선

#### B등급: 게임/진행 이벤트

영구 기록하되, 집계 중심으로 처리한다.

- 미니게임 시작/성공/퍼펙트/스피드 보너스
- 로그인/하루 첫 접속
- 대표 카드/상태 메시지 변경
- 카드 숨김/잠금/즐겨찾기

처리:

- 원본 이벤트 기록
- 집계 즉시 갱신
- 복합 업적은 큐 평가

#### C등급: 탐색/커뮤니티 이벤트

영구 기록하되, 이벤트 수를 제한한다.

- 화면 진입
- 친구 신청/수락
- 채팅 메시지 전송
- 이미지 첨부
- 신고 접수

처리:

- 일 단위 dedupe 또는 인정 상한 적용
- 원문 저장 금지
- 낮은 보상 또는 1회성 업적 중심

### 19.8 권장 구현 순서

1. `achievement_events`와 `user_achievement_stats`를 먼저 추가한다.
2. A등급 이벤트만 연결한다.
3. 업적 화면은 `user_achievements`와 `user_achievement_stats`만 읽게 만든다.
4. 평가 큐를 추가해 복합/무거운 조건을 분리한다.
5. B등급 이벤트를 확장한다.
6. C등급 이벤트는 일일 상한과 dedupe 정책을 먼저 만든 뒤 연결한다.

## 20. 구현 필수 준수사항

아래 항목은 권장사항이 아니라 업적 시스템 구현 시 반드시 지켜야 하는 제약이다. 이 제약을 만족하지 않는 업적 정의, API, 관리자 기능, 보상 지급 로직은 배포하지 않는다.

### 20.1 보상 지급 필수 규칙

- 모든 보상 지급은 멱등 처리해야 한다.
- 같은 `user_id + achievement_id + repeat_key` 조합으로 보상이 2회 이상 지급되면 안 된다.
- 보상 지급 전 `achievement_grant_logs` 또는 동등한 유니크 제약을 확인해야 한다.
- 보상 지급과 `user_achievements.claimed_at/status` 갱신은 원자적으로 처리해야 한다.
- 보상 일부만 지급되고 상태만 수령 완료가 되는 상황을 허용하지 않는다.
- 보상 지급 실패 시 실패 로그를 남겨야 하며, 유저에게는 재시도 가능한 상태로 남겨야 한다.
- 자동 지급 업적도 직접 수령 업적과 동일한 멱등 키를 사용해야 한다.
- 포인트, 카드, 티켓, 코스메틱, 칭호 보상은 기존 자산 감사 로그에도 남겨야 한다.
- 보상 수량은 서버에서 검증해야 하며, 음수/0/비정상적으로 큰 값은 저장하거나 지급하지 않는다.
- 반복 업적은 반드시 `repeat_key`를 가진다. `repeat_key` 없는 반복 보상은 금지한다.

### 20.2 경제 밸런스 필수 규칙

- 업적 정의에는 보상 총량을 계산할 수 있는 `rewards_json`만 허용한다.
- 관리자 생성/수정 화면은 저장 전에 보상 위험도를 표시해야 한다.
- 포인트/티켓/카드 보상이 있는 업적은 활성화 전 미리보기 검증을 통과해야 한다.
- 기간 한정 업적은 `starts_at` 또는 `ends_at` 중 최소 하나를 명시해야 한다.
- 반복 업적은 기본값을 비활성으로 두고, 일/주/월/시즌 보상 상한을 설정해야 한다.
- 숨겨진 업적은 큰 경제 보상을 기본으로 금지한다. 필요하면 별도 관리자 확인 절차를 둔다.
- 거래/마켓/채팅/신고처럼 반복 조작이 쉬운 행동에는 고액 보상을 주지 않는다.
- 업적별 누적 지급량을 관리자에서 조회할 수 있어야 한다.

### 20.3 어뷰징 방지 필수 규칙

- 클라이언트가 진행도 증가를 직접 요청하는 API를 만들지 않는다.
- 업적 이벤트는 서버 액션 성공 이후 서버 코드가 직접 기록한다.
- 실패한 액션, 검증 실패, 취소된 요청은 기본적으로 진행도에 반영하지 않는다.
- 채팅 메시지 수, 친구 신청 수, 신고 수, 교환 제안 수, 화면 진입 수는 일일 인정 상한 또는 dedupe 정책이 필수다.
- 교환 관련 주요 업적은 “제안 생성”보다 “성사” 기준을 우선한다.
- 마켓 관련 주요 업적은 “등록”보다 “판매/구매/낙찰 성사” 기준을 우선한다.
- 신고 업적은 단순 신고 횟수 반복 보상을 금지한다. 운영 승인 또는 처리 완료 기준만 보상 가능하다.
- 채팅 업적은 메시지 원문, 이미지 내용, 상대방 개인정보를 조건으로 사용하지 않는다.
- 자전거래나 반복 이동으로 달성 가능한 업적은 고유 대상 수, 순증가, 성사 횟수, 일일 상한 중 하나 이상을 조건에 포함해야 한다.
- 동일 이벤트가 재시도되어도 `event_key` unique로 1회만 인정해야 한다.

### 20.4 숨겨진 업적 필수 규칙

- 숨겨진 미달성 업적의 이름, 설명, 조건, 목표 수치, 진행도, 보상 상세는 API 응답에 포함하지 않는다.
- 프론트에서만 숨기는 방식은 금지한다. 서버 DTO 생성 단계에서 마스킹해야 한다.
- 숨겨진 미달성 업적은 `???`, 숨겨진 업적 여부, 선택적 힌트만 내려준다.
- 힌트는 관리자가 명시적으로 설정한 경우에만 내려준다.
- 숨겨진 업적이 달성된 뒤에는 달성자 본인에게만 상세 정보를 공개한다.
- 관리자 미리보기 API와 일반 유저 API의 응답 타입을 분리한다.

### 20.5 DB/백엔드 부하 필수 규칙

- 핵심 서비스 요청 중 업적 전체 목록을 매번 평가하지 않는다.
- 카드 뽑기, 미니게임 제출, 마켓 구매, 교환 성사 같은 핵심 요청에서는 이벤트 기록과 가벼운 집계 갱신까지만 수행한다.
- 복합 조건, 시즌 조건, 전체 재계산은 큐 또는 배치 워커에서 처리한다.
- 유저 업적 화면은 `achievement_events` 원본을 직접 집계하지 않는다.
- 유저 업적 화면은 `user_achievements`와 `user_achievement_stats` 중심으로 조회한다.
- `achievement_events.metadata_json`에는 큰 객체, HTML, Markdown, 이미지 URL 대량 배열, 원문 텍스트를 저장하지 않는다.
- 원본 이벤트 테이블에는 필요한 최소 인덱스만 둔다.
- 관리자 감사 조회는 cursor 기반 페이지네이션을 사용한다.
- 대량 재계산 API는 한 번에 전체 유저를 동기 처리하지 않는다.
- 동일 유저의 평가 큐는 dedupe해야 한다.
- 업적 정의는 메모리 캐시하고, 관리자 수정 시 캐시 무효화가 되어야 한다.

### 20.6 개인정보/민감정보 필수 규칙

- 채팅 메시지 원문은 업적 이벤트에 저장하지 않는다.
- 검색어 원문은 업적 이벤트에 저장하지 않는다.
- 쿠폰 코드 원문은 업적 이벤트에 저장하지 않는다.
- 신고 상세 사유 원문은 업적 이벤트에 저장하지 않는다.
- 외부 프로필 이미지 URL, 카드 이미지 URL은 업적 이벤트에 반복 저장하지 않는다.
- 업적 이벤트에는 가능한 한 내부 ID, enum, 숫자, boolean만 저장한다.
- 회원 탈퇴 시 업적 이벤트의 유저 식별자 처리 정책을 명확히 적용해야 한다.
- 개인정보 처리방침과 충돌하는 신규 이벤트를 추가하지 않는다.

### 20.7 관리자 기능 필수 규칙

- 관리자 업적 생성/수정 API는 허용된 메트릭, 연산자, 필터, 보상 타입만 저장할 수 있게 검증한다.
- 관리자가 임의 SQL, 임의 JS, 임의 식을 조건으로 저장할 수 없게 한다.
- `criteria_json`과 `rewards_json`은 저장 전 스키마 검증을 통과해야 한다.
- 알 수 없는 메트릭은 저장하지 않는다.
- 삭제된/비활성 상점 아이템, 존재하지 않는 칭호, 존재하지 않는 스트리머 카드 보상은 저장 단계에서 경고하거나 차단한다.
- 업적 수정 시 이미 완료한 유저에게 미치는 영향을 관리자에게 보여줘야 한다.
- 보상이 있는 업적을 활성화할 때는 확인 단계를 둔다.
- 업적 복제 시 기본값은 비활성으로 둔다.
- 관리자 미리보기는 특정 유저 기준 진행도와 예상 보상을 보여줘야 한다.
- 운영자가 전체 재계산을 실행할 경우 예상 처리 범위와 큐 적재량을 확인하게 해야 한다.

### 20.8 일관성/복구 필수 규칙

- `achievement_events`는 원본 이벤트로 영구 보존한다.
- `user_achievement_stats`는 원본 이벤트로 재생성 가능해야 한다.
- 집계 갱신 실패 시 재시도 가능한 큐 또는 보정 작업이 있어야 한다.
- 업적 평가 로직은 같은 입력에 대해 같은 결과를 내야 한다.
- 시간 기준 업적은 `Asia/Seoul` 기준인지 UTC 기준인지 업적 정의에 명시해야 한다.
- 일/주/월 반복 업적의 `repeat_key` 생성 규칙은 서버 공통 함수로 통일한다.
- 배치 재계산은 이미 수령한 보상을 취소하거나 중복 지급하지 않아야 한다.
- 업적 완료 이후 스냅샷 조건이 다시 미달되어도 기본적으로 완료 상태를 취소하지 않는다.

### 20.9 출시 순서 필수 규칙

- 1차 출시에는 A등급 자산/보상 핵심 이벤트와 낮은 리스크 업적만 포함한다.
- 채팅/친구/신고/화면 진입 업적은 dedupe와 일일 상한 구현 전 출시하지 않는다.
- 반복 보상 업적은 누적 지급량 모니터링 화면 없이 출시하지 않는다.
- 숨겨진 업적은 서버 마스킹 테스트 없이 출시하지 않는다.
- 보상 지급 업적은 중복 지급 테스트 없이 출시하지 않는다.
- 업적 시스템 도입 후 관리자에서 업적별 달성자 수와 지급량을 확인할 수 있어야 한다.

### 20.10 테스트 필수 항목

- 같은 업적 보상을 동시에 두 번 수령 요청해도 1회만 지급된다.
- 서버 재시도나 동일 이벤트 재기록 상황에서도 진행도가 중복 증가하지 않는다.
- 숨겨진 미달성 업적 API 응답에 이름, 설명, 조건, 진행도, 보상이 포함되지 않는다.
- 비활성 업적은 새로 진행되지 않는다.
- 기간 종료 업적은 새로 진행되지 않는다.
- 반복 업적은 `repeat_key`별로만 보상이 지급된다.
- 관리자 조건 빌더가 허용되지 않은 메트릭/필터/보상을 차단한다.
- 보상 지급 실패 시 재수령 가능한 상태로 남는다.
- 유저 업적 목록 조회가 원본 이벤트 전체 스캔을 하지 않는다.
- 대량 이벤트 기록 시 핵심 API 응답 시간이 과도하게 늘지 않는다.
