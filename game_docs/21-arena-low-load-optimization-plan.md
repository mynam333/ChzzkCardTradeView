# 치카포 아레나 초저부하 최적화 계획

## 1. 목적

이 문서는 치카포 아레나를 6GB RAM + 4GB swap 서버에서 본편과 MySQL에 부담을 주지 않도록 운영하기 위한 초저부하 기본값을 정의한다.

기본 방향은 “기능을 제공하되, 비싼 기능은 기본적으로 줄이고 필요할 때만 켠다”이다.

## 2. 최상위 원칙

- 본편 API 지연이 증가하면 아레나 기능을 즉시 줄인다.
- 빠른대전보다 본편 안정성이 우선이다.
- 봇전보다 빠른대전이 우선이다.
- 상세 리플레이보다 매치 결과 무결성이 우선이다.
- 실시간 랭킹보다 서버 안정성이 우선이다.
- 실시간 공개 리플레이 방송, 실시간 관전방, 실시간 상주 매치룸은 MVP에서 금지한다. 완료된 리플레이 기반 관전은 제한적으로 허용한다. 빠른대전/컵 큐 상태만 대기 중 일시 SSE 연결을 허용하며, 매칭·취소·만료 후 즉시 닫는다.

## 3. MVP 초저부하 기본값

| 항목 | 기본값 |
| --- | --- |
| 빠른대전 동시 시뮬레이션 | 1~2개 워커 |
| 봇전 동시 시뮬레이션 | 0~1개 워커 |
| 봇전 피크 시간 | 자동 제한 또는 중단 |
| 랭킹 스냅샷 | 상위 1000명 우선 |
| 전체 랭킹 스냅샷 | 30~60분 또는 수동 |
| 상세 리플레이 | 랭킹전 최근 경기만 짧게 |
| 봇전 상세 리플레이 | 기본 미저장 |
| 리플레이 TTL | MVP 7일 이하부터 시작 |
| 카드 목록 | 캐시 필수 |
| 카드 상세 | 캐시 필수 |
| 카드 능력 생성 | 배치 생성 후 저장 |
| 매칭 상태 전송 | 큐 대기 중 SSE 우선, HTTP fallback 30~90초 |
| 큐 TTL | 60초 |
| 완료 리플레이 관전 | 제한 허용, 강한 rate limit |

## 4. 리플레이 최적화

리플레이는 가장 먼저 비용을 줄인다.

### 4.1 저장 단계

MVP 기본:

- 매치 요약은 저장한다.
- 라운드 결과는 저장한다.
- MVP 하이라이트 이벤트만 저장한다.
- 상세 이벤트 로그는 랭킹전 최근 경기만 저장한다.
- 봇전 상세 이벤트 로그는 저장하지 않는다.

상세 로그 저장 조건:

- 랭킹전
- 정상 종료 매치
- 로그 크기 상한 이하
- 서버 부하 정상
- 저장 공간 정상

저장하지 않는 경우:

- 봇전
- 비정상 종료 매치
- 이벤트 수 상한 초과
- 서버 부하 위험
- 리플레이 kill switch 활성

### 4.2 저장 형식

금지:

- MySQL JSON 컬럼에 원본 이벤트 장기 저장
- 프레임 단위 좌표 저장
- 모든 봇전 리플레이 저장
- 공개 리플레이용 썸네일 자동 생성

허용:

- 압축 `MEDIUMBLOB`
- 파일 저장 후 `log_ref`만 DB 저장
- 요약 이벤트만 저장
- 만료 후 summary fallback

### 4.3 삭제 정책

삭제 배치는 작게 나누어 실행한다.

권장:

```text
DELETE_LIMIT = 500
DELETE_INTERVAL_SEC = 10~60
```

디스크 여유가 부족하면:

1. 봇전 로그 즉시 삭제
2. 랭킹전 상세 로그 TTL 축소
3. 리플레이 상세 조회 중단
4. 신규 상세 로그 저장 중단

## 5. 전투 시뮬레이션 최적화

전투 시뮬레이터는 DB에 접근하지 않는다.

원칙:

- 입력은 덱 스냅샷과 시즌 룰만 사용한다.
- 시뮬레이션 중 DB 조회 금지
- 시뮬레이션 중 DB 쓰기 금지
- 결과 저장은 라운드 계산 완료 후 짧은 단일 update로 처리한다.
- 매치 생성은 1회 insert, 라운드 확정은 최대 5회 update만 허용한다.
- 세트 전체를 시작 시점에 미리 계산하지 않는다.
- 시간 초과 시 실패 처리하고 재시도하지 않는다.

워커 기본값:

```text
RANKED_SIM_WORKERS = 1
BOT_SIM_WORKERS = 0
MAX_SIM_WORKERS = 2
```

증설 조건:

- 본편 API p95 변화 없음
- MySQL CPU 안정
- Node.js RSS 안정
- round simulation p95 150ms 이하 유지

축소 조건:

- round simulation p95 500ms 초과
- Node.js event loop delay 증가
- MySQL CPU 위험
- swap 사용량 증가

## 6. 매칭 큐 최적화

큐 매칭은 인덱스를 타는 방식만 사용한다.

금지:

- `ABS(mmr - my_mmr)` 기반 대량 정렬
- 전체 WAITING 큐 스캔
- 큐 상태를 오래 유지
- 한 유저의 중복 WAITING row 허용

권장 구조:

- MMR을 50점 또는 100점 단위 bucket으로 저장한다.
- 먼저 같은 bucket을 조회한다.
- 대기 시간이 길어지면 인접 bucket을 조회한다.
- 후보 row 수를 제한한다.
- 후보 중 최종 선택은 애플리케이션 메모리에서 처리한다.

추가 컬럼:

```text
mmr_bucket INT NOT NULL
```

권장 인덱스:

```sql
INDEX idx_arena_queue_bucket (season_id, status, mmr_bucket, queued_at)
INDEX idx_arena_queue_user_status (user_id, status)
INDEX idx_arena_queue_expire (expires_at)
```

매칭 후보 제한:

```text
MAX_QUEUE_CANDIDATES = 20
```

### 6.1 이탈 처리 최적화

게임 중 이탈을 부하 없이 처리하기 위해 클라이언트 연결 상태를 실시간 추적하지 않는다.

금지:

- 브라우저 unload 이벤트마다 cancel API 호출 강제
- 유저별 heartbeat row를 1초 단위로 갱신
- 리플레이 시청 위치를 매초 저장
- 상대 접속 여부를 전투 진행 조건으로 사용

권장:

- 큐는 60초 TTL로 자연 만료시킨다.
- 매칭 완료 후에는 match id가 재접속 토큰 역할을 한다.
- status API는 SSE 재접속/fallback 용도로만 사용하며 최소 3초 이상의 간격과 private no-store 응답만 사용한다.
- 리플레이 진행 위치는 localStorage 또는 클라이언트 상태로만 저장한다.
- 한쪽이 라운드 전술을 제출하면 기본 선택 타이머 동안 상대 입력을 기다린다.
- 타이머가 끝난 뒤에도 라운드 전술 미제출자는 저장된 기본 라운드 플랜으로 자동 진행한다.
- 양쪽 유저가 모두 이탈해도 `arena-worker`가 `arena_matches.pending_round_deadline_at` 인덱스로 만료 라운드만 제한 개수 조회해 자동 커밋한다.
- 상대 접속 여부를 감시하는 상주 룸, heartbeat, DB 상태 write를 만들지 않는다.
- 자동 진행은 별도 워커가 아니라 참가자의 라운드 커밋 요청 시점에 처리한다.
- 반복 큐 취소 카운터는 Redis가 없으면 짧은 DB 집계보다 rate limit 미들웨어와 최근 요청 메모리 캐시를 우선한다.

## 7. 랭킹 최적화

랭킹 조회는 항상 스냅샷 기반이다.

MVP 기준:

- 상위 1000명만 기본 스냅샷
- 내 순위는 본인 rating row 기준으로 대략 표시 가능
- 전체 순위 정확도는 시즌 종료 정산 시 보정
- 실시간 전체 랭킹 정렬 금지

스냅샷 생성:

- 피크 시간에는 갱신 주기 늘림
- MySQL 부하가 있으면 갱신 건너뜀
- 시즌 종료 직전에는 별도 점검 창에서 최종 스냅샷 생성

권장:

```text
TOP_RANK_REFRESH_SEC = 300
FULL_RANK_REFRESH_SEC = 3600
RANK_SNAPSHOT_LIMIT = 1000
```

## 8. 카드 조회 최적화

카드 수 3천 장은 크지 않지만, 필터/검색/정렬이 반복되면 누적 부하가 생긴다.

원칙:

- 카드 목록은 캐시한다.
- 카드 상세는 캐시한다.
- 전체 활성 카드 사용 가능 상태는 캐시한다.
- 덱 검증은 캐시된 카드 버전 정보를 사용한다.
- 카드 능력은 요청 시 생성하지 않는다.

권장 캐시:

```text
arena:season:current
arena:card-availability:{season_id}:{version}
arena:card:{card_id}:{card_version}
arena:card-list:{season_id}:{filter_hash}
arena:skill-defs:{version}
arena:tag-defs:{version}
```

캐시 무효화:

- 시즌 변경
- 카드 사용 가능 상태 재검증
- 스트리머 비활성화
- 관리자 카드 제한
- generation version 변경

## 9. 봇전 최적화

봇전은 연습 기능이지만 서버 비용은 랭킹전과 비슷하다.

MVP 기준:

- 봇 덱은 미리 생성한다.
- 봇전 상세 로그는 저장하지 않는다.
- 봇전은 MMR/랭킹/보상에 반영하지 않는다.
- 피크 시간에는 봇전을 먼저 제한한다.
- 봇전 워커는 랭킹전 워커와 분리하거나 낮은 우선순위로 둔다.

권장 제한:

```text
BOT_MATCH_LIMIT = 10회 / 10분 / user
BOT_REPLAY_SAVE = false
BOT_PRIORITY = low
```

## 10. DB 쓰기 최적화

매치 종료 시 최소 쓰기만 수행한다.

필수 쓰기:

- `arena_matches`
- `arena_player_ratings`
- `arena_rating_history`
- 필요 시 `arena_battle_logs`

주의:

- match summary와 rating은 같은 트랜잭션으로 처리한다.
- battle log 저장 실패는 match/rating 성공을 되돌리지 않는다.
- 리플레이 실패와 경기 결과 실패를 분리한다.
- idempotency key로 중복 반영을 막는다.

금지:

- 매치마다 전체 랭킹 갱신
- 매치마다 카드/클래스/스킬 통계 전체 갱신
- 매치마다 대량 로그 insert
- 매치 결과 저장 트랜잭션 안에서 시뮬레이션 실행

## 11. 배치 작업 최적화

배치 작업은 작게, 자주, 중단 가능하게 만든다.

대상:

- 큐 만료
- 리플레이 로그 삭제
- 랭킹 스냅샷 생성
- 카드 생성 배치
- 밸런스 통계 집계

원칙:

- limit 기반 처리
- 처리 시간 상한
- 실패 시 다음 배치로 넘김
- 피크 시간 자동 중지 가능
- 본편 API 부하 감지 시 중단

## 12. 캐시 우선순위

반드시 캐시:

1. 현재 시즌
2. 전체 활성 카드 사용 가능 상태
3. 카드 상세
4. 스킬/태그 정의
5. 랭킹 스냅샷
6. 시스템 kill switch 상태

캐시 없이 허용 가능한 것:

- 본인 덱 목록
- 본인 최근 매치 요약
- 본인 rating row

## 13. 운영 중 자동 제한 기준

아래 조건 중 하나라도 만족하면 자동 제한을 검토한다.

```text
MySQL CPU high 5분 지속
Node.js RSS 지속 증가
swap 사용량 증가
quick join p95 1초 초과
set simulation p95 1초 초과
battle log 저장 실패율 증가
ranking snapshot 실패
disk free 부족
```

제한 순서:

1. 봇전 중단
2. 상세 리플레이 저장 중단
3. 상세 리플레이 조회 중단
4. 랭킹 스냅샷 갱신 주기 증가
5. 빠른대전 신규 큐 중단
6. 아레나 전체 점검

## 14. 구현 전 체크리스트

- 시뮬레이터가 DB에 접근하지 않는가?
- 매치 저장 트랜잭션이 짧은가?
- 리플레이 로그 저장 실패가 경기 결과를 망치지 않는가?
- 봇전 상세 로그를 기본 저장하지 않는가?
- 랭킹 조회가 스냅샷만 읽는가?
- 매칭 큐가 MMR bucket 인덱스를 타는가?
- 카드 목록/상세가 캐시되는가?
- kill switch가 기능별로 동작하는가?
- 배치 작업이 limit 기반인가?
- 본편 API 지표를 보고 아레나를 제한할 수 있는가?

## 13. 확장 모드 저부하 기준

### 13.1 5판 3선승

- `MAX_ROUNDS_PER_MATCH = 5`
- `ROUNDS_TO_WIN = 3`
- `MAX_ROUND_TICKS = 180`
- `MAX_MATCH_TICKS = 900`
- 상세 이벤트 로그는 상한 초과 시 요약 이벤트로 압축한다.
- 서버는 7~12분 동안 매치를 메모리에 들고 있지 않는다.

### 13.2 8인 컵

- 컵 동시 처리 수는 0~1개로 시작한다.
- 피크 시간에는 컵 생성 중단 가능.
- 컵 상세 로그는 본인 경기/결승/하이라이트만 저장.
- 컵 통계는 스냅샷으로만 조회.

### 13.3 관전

- 완료된 리플레이/하이라이트만 관전 가능.
- 실시간 tick broadcast 금지.
- 관전자 진행 위치 서버 저장 금지.
- 관전 공유 링크는 토큰 기반이며 만료 시각과 rate limit 필수.

### 13.4 관리자 통계

- 관리자 화면 요청 시 대량 `GROUP BY` 금지.
- 통계 스냅샷은 30~60분 또는 수동 생성.
- 표본 수가 작은 통계는 숨김.
- 통계 재생성은 관리자 rate limit과 kill switch 적용.

금지:

- 밴픽
- 시즌 로테이션 카드 풀
- 실시간 관전방
- 컵 전체 상세 리플레이 장기 저장
## 12. 구현 보강 반영 사항

2026-06-25 구현 기준으로 다음 운영 안전장치를 필수 정책으로 둔다.

- 아레나 핵심 테이블은 서비스 첫 요청이 아니라 DB 초기화 단계에서도 선제 생성한다.
- 빠른대전 큐와 8인 컵 큐는 관리자 복구 API를 제공한다.
- 큐 복구는 `status`, `expires_at`, `season_id` 인덱스를 사용하는 bounded update만 허용한다.
- 통계 스냅샷 재생성, 랭킹 스냅샷 재생성, 리플레이 정리는 관리자 job으로 등록하고 백그라운드에서 실행한다.
- 관리자 job은 `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED` 상태를 기록한다.
- 리플레이 저장은 `ARENA_REPLAY_MAX_EVENTS_PER_ROUND`, `ARENA_REPLAY_MAX_BYTES` 상한을 넘지 않는다.
- 신규 일반 매치 리플레이는 `arena_match_replays`, 8인 컵 리플레이는 `arena_cup_replays`에 분리 저장하고, 본문 테이블의 `replay_json`은 레거시 fallback으로만 사용한다. `replay_prune`은 두 리플레이 테이블과 레거시 inline 값을 함께 제한 개수로 정리한다. 큐 상태는 상태 변화 이벤트를 SSE로 즉시 전달하고, fallback 조회는 30~90초 수준으로 늦춘다.
- `ARENA_DISABLE_REPLAY_WRITES=true`일 때 신규 리플레이 저장을 중지한다.
- `ARENA_DISABLE_RANKED_RATING_WRITES=true`일 때 랭크 매치 결과는 저장하되 MMR 갱신은 중지한다.
- 관리자 화면은 빠른대전 큐, 8인 컵 큐, 최근 관리자 job 상태를 스냅샷으로 표시한다.
